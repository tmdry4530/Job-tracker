# Product Requirements Document - Job Application Tracker

**Author:** Wjdtm
**Date:** 2026-01-03

## Executive Summary

**Job Application Tracker**는 국내 채용 플랫폼(원티드, 사람인)에 흩어진 지원 현황을 한 곳에서 통합 관리하는 서비스입니다.

구직자들은 매일 30분~1시간을 여러 플랫폼을 오가며 지원 현황을 확인하는 데 낭비합니다. 노션이나 엑셀로 수동 관리를 시도하지만, 대부분 2~3일 만에 포기합니다. 그 결과 면접에서 JD 내용을 까먹거나, 중복 지원하거나, 면접 일정을 놓치는 일이 빈번합니다.

이 제품은 크롬 익스텐션으로 지원 데이터를 **자동 수집**하고, Claude API로 JD를 **핵심 요약**하며, **면접 예상 질문**을 자동 생성합니다. 해외에는 Huntr, Teal 같은 job tracker가 있지만 국내 플랫폼은 지원하지 않으며, 이 제품이 그 공백을 채웁니다.

### What Makes This Special

| 차별화 요소 | 설명 |
|-------------|------|
| **자동 수집** | 수동 입력 불필요 → 지속 가능한 사용성 (핵심 중 핵심) |
| **AI JD 요약** | 면접 5분 전 핵심만 빠르게 복습 |
| **면접 예상 질문** | JD 기반 맞춤형 준비 자료 자동 생성 (Aha! 순간) |
| **국내 플랫폼 특화** | 원티드, 사람인 네이티브 지원 (해외 서비스 불가) |

### Journey 1: 김지원 - 30개 지원의 혼란에서 벗어나기

**페르소나**: 신입 취준생 (메인) | **유형**: 성공 경로

**김지원**은 부트캠프를 막 수료한 신입 프론트엔드 개발자다. React와 TypeScript를 배웠고, 포트폴리오도 준비했다. 문제는 취업 시장이 만만치 않다는 것. "일단 많이 넣어봐야 한다"는 선배들 조언대로 원티드와 사람인에서 보이는 포지션마다 지원하기 시작했다.

2주 만에 지원한 공고가 30개를 넘었다. 처음엔 노션에 표를 만들어 관리하려 했지만, 3일 만에 포기했다. 지원할 때마다 표를 업데이트하는 게 귀찮았고, 이미 10개 이상 누락된 상태였다. 어느 날 밤, 모르는 번호로 전화가 왔다. "안녕하세요, OO회사 채용 담당자입니다. 면접 일정 조율하려고요." 지원은 기쁜데... **이 회사가 뭐하는 곳이었지?** 전화를 끊고 원티드 앱을 열어 뒤적였지만, 비슷비슷한 공고 30개 중에 해당 회사를 찾는 데만 10분이 걸렸다.

그날 밤, 개발자 오픈카톡방에서 누군가 공유한 **Job Application Tracker**를 발견한다. "지원 자동 수집된다고?" 반신반의하며 크롬 익스텐션을 설치했다. 원티드 지원현황 페이지에 가니 **기존 지원 28개가 자동으로 정리되어 대시보드에 떴다.** "와, 이게 되네?" 사람인도 마찬가지였다. 흩어져 있던 모든 지원 내역이 한 화면에 보였다.

다음 날, 또 면접 연락이 왔다. 이번엔 대시보드에서 회사명을 검색했다. **5초 만에 찾았다.** JD 요약을 보니 "React + TypeScript, 스타트업, 팀 규모 5명, 핵심 업무: 어드민 대시보드 개발"이 한눈에 들어왔다. 면접 예상 질문도 이미 생성되어 있었다. "왜 프론트엔드를 선택했나요?", "React와 Vue의 차이점은?", "이 포지션에서 어떤 성장을 기대하시나요?"

면접 당일, 지하철에서 10분 동안 JD 요약과 예상 질문만 훑어봤다. 면접장에서 면접관이 물었다. "저희 회사 어드민 대시보드 알고 계시죠? 어떻게 개선하면 좋을까요?" 지원은 JD에서 본 "레거시 어드민 리뉴얼" 키워드가 떠올랐고, 준비한 대로 답변했다. 면접관의 표정이 밝아졌다.

2주 뒤, 지원이는 그 회사에서 합격 통보를 받았다. 첫 취업이었다. 남아있는 다른 면접들도 대시보드에서 관리하며 진행했고, 최종 입사할 회사를 고르는 행복한 고민을 하게 됐다.

> **"지원 많이 하는 게 죄가 아니었어. 관리가 안 되는 게 문제였을 뿐."**

### Journey 2: 김지원 - 서류 탈락 알림과 상태 업데이트

**페르소나**: 신입 취준생 (메인) | **유형**: 엣지 케이스

같은 김지원. 30개 중 20개에서 서류 탈락 메일이 오기 시작했다. 예전 같으면 어디서 떨어졌는지도 모르고 넘어갔을 텐데, 이제는 대시보드에서 해당 공고를 찾아 **상태를 "서류 탈락"으로 변경**한다.

처음엔 귀찮았다. "이것도 수동이잖아?" 하지만 상태를 바꾸고 나니 **남은 10개가 뭔지 명확해졌다.** "진행 중" 필터를 걸면 아직 결과가 안 나온 공고만 보였다. 더 이상 "이 회사는 결과 나왔나?" 하며 플랫폼마다 로그인해서 확인할 필요가 없어졌다.

어느 날, 원티드에서 "지원하기" 버튼을 눌렀는데 **"이미 지원한 공고입니다"** 알림이 떴다. 대시보드에서 검색해보니 2주 전에 지원했던 곳이었다. 서류 탈락 후 재공고된 것이다. **중복 지원을 피했다.** 민망한 상황을 모면한 지원이는 안도했다.

> **"수동 상태 변경이 조금 귀찮아도, 30개 지원 중 어디가 진행 중인지 한눈에 보이는 게 더 가치있어."**

### Journey 3: 박민수 - 퇴근 후 15분의 비밀 이직 준비

**페르소나**: 재직 중 이직러 (서브) | **유형**: 성공 경로

**박민수**는 3년차 백엔드 개발자다. 현 직장도 나쁘지 않지만, 더 큰 도전을 원한다. 문제는 시간이 없다는 것. 이직 준비는 퇴근 후 피곤한 몸을 이끌고 하거나, 점심시간 15분을 쪼개서 해야 한다. 회사에서 들킬까 봐 조심하면서.

민수는 일주일에 5~10개 정도 지원한다. 양보다 질이라 생각하며 신중하게 고른다. 하지만 정작 면접이 잡히면 "이 회사 JD가 뭐였지?" 하며 다시 찾아봐야 한다. 퇴근 후 피곤한 밤, 면접 준비에 2~3시간을 쏟는 건 체력적으로 버겁다.

Job Application Tracker를 알게 된 민수는 **점심시간에 지원하고, 자동 수집 확인하고, JD 요약을 읽는 루틴**을 만들었다. 면접이 잡히면 출근길 지하철에서 JD 요약과 예상 질문만 훑는다. 30분이면 충분했다.

면접 전날 밤 11시까지 JD 읽으며 끙끙대던 예전과 달리, 이제 10시에 잠자리에 든다. 다음날 면접에서 훨씬 맑은 정신으로 답변할 수 있었다.

> **"이직 준비가 덜 고통스러워졌어. 시간이 없는 게 아니라, 낭비하고 있던 거였어."**

### 구현 고려사항

## Project Scoping & Phased Development

### MVP 전략 & 철학

**MVP 접근 방식:** Problem-Solving + Experience MVP 하이브리드
- 핵심 문제(지원 관리 혼란) 해결
- 핵심 경험(자동 수집, JD 요약, 예상 질문) 제공

**프로젝트 규모:** Medium scope (2-3주 개발)
**개발 리소스:** 1인 개발 (본인)

### MVP Feature Set (Phase 1)

**지원되는 핵심 여정:**
- Journey 1: 신입 취준생 - 30개 지원의 혼란에서 벗어나기
- Journey 2: 신입 취준생 - 서류 탈락/상태 관리
- Journey 3: 재직 중 이직러 - 빠른 복습

**Must-Have 기능 (8개):**

| # | 기능 | 컴포넌트 | 여정 근거 |
|---|------|----------|-----------|
| 1 | 원티드 지원내역 파싱 | Extension | Journey 1, 3 |
| 2 | 사람인 지원내역 파싱 | Extension | Journey 1 |
| 3 | 지원 목록 보기 | Dashboard | 모든 여정 |
| 4 | 검색/필터 | Dashboard | Journey 1, 2 (대량 관리) |
| 5 | JD 요약 | AI | Journey 1, 3 (핵심 가치) |
| 6 | 면접 예상 질문 | AI | Journey 1, 3 (Aha! 순간) |
| 7 | 상태 수동 변경 | Dashboard | Journey 2 (진행 추적) |
| 8 | 로그인/회원가입 | Dashboard | 기본 요구 |

### Risk Mitigation Strategy

| 리스크 유형 | 리스크 | 완화 전략 |

## Functional Requirements

> **⚠️ 기능 계약**: 이 목록에 없는 기능은 최종 제품에 포함되지 않습니다.

### 1. 사용자 인증 (User Authentication)

- **FR1**: 사용자는 이메일/비밀번호로 회원가입할 수 있다
- **FR2**: 사용자는 이메일/비밀번호로 로그인할 수 있다
- **FR3**: 사용자는 로그아웃할 수 있다
- **FR4**: Chrome Extension은 Dashboard 로그인 상태를 공유한다

### 2. 지원 데이터 수집 (Application Data Collection)

- **FR5**: Extension은 원티드 "지원현황" 페이지에서 기존 지원 내역을 파싱할 수 있다
- **FR6**: Extension은 사람인 "지원현황" 페이지에서 기존 지원 내역을 파싱할 수 있다
- **FR7**: Extension은 파싱한 데이터를 백엔드에 동기화할 수 있다
- **FR8**: Extension은 새로운 지원 발생 시 자동으로 감지하여 수집할 수 있다

### 3. 지원 현황 관리 (Application Management)

- **FR9**: 사용자는 모든 지원 공고를 목록으로 볼 수 있다
- **FR10**: 사용자는 회사명 또는 포지션명으로 지원 공고를 검색할 수 있다
- **FR11**: 사용자는 플랫폼(원티드/사람인)으로 지원 공고를 필터링할 수 있다
- **FR12**: 사용자는 지원 상태(지원완료/서류통과/면접진행/합격/불합격)로 필터링할 수 있다
- **FR13**: 사용자는 지원 공고의 상태를 수동으로 변경할 수 있다
- **FR21**: 사용자는 지원 공고를 삭제할 수 있다

### 4. AI 분석 (AI Analysis)

- **FR14**: 시스템은 JD(Job Description)를 핵심 내용으로 요약할 수 있다
- **FR15**: 시스템은 JD 기반으로 면접 예상 질문을 생성할 수 있다
- **FR16**: 사용자는 특정 공고의 JD 요약을 조회할 수 있다
- **FR17**: 사용자는 특정 공고의 면접 예상 질문을 조회할 수 있다

### 5. 공고 상세 (Application Details)

- **FR18**: 사용자는 지원 공고의 상세 정보(회사명, 포지션, 지원일, 플랫폼 등)를 볼 수 있다
- **FR19**: 사용자는 원본 JD 전문을 볼 수 있다
- **FR20**: 사용자는 지원 공고의 원본 URL로 이동할 수 있다

## Non-Functional Requirements

> **품질 계약**: MVP 출시 전 모든 NFR 충족 필요

### 1. Performance (성능)

- **P1**: 대시보드 페이지 초기 로딩은 2초 이내에 완료되어야 한다
- **P2**: 검색/필터 결과는 500ms 이내에 반환되어야 한다
- **P3**: JD 요약 생성은 5초 이내에 완료되어야 한다 (Claude API 포함)
- **P4**: Extension DOM 파싱은 3초 이내에 완료되어야 한다

### 2. Security (보안)

- **S1**: 모든 사용자 데이터는 HTTPS로 전송되어야 한다
- **S2**: 비밀번호는 해시 처리되어 저장되어야 한다 (Supabase Auth 기본 제공)
- **S3**: API 엔드포인트는 인증된 사용자만 접근 가능해야 한다
- **S4**: Claude API 키는 서버 사이드에서만 사용되어야 한다
- **S5**: 사용자는 본인의 지원 데이터만 조회할 수 있어야 한다 (Row Level Security)

### 3. Reliability (신뢰성)

- **R1**: 원티드 파서는 95% 이상의 성공률을 유지해야 한다
- **R2**: 사람인 파서는 90% 이상의 성공률을 유지해야 한다
- **R3**: 파싱 실패 시 사용자에게 명확한 에러 메시지를 표시해야 한다
- **R4**: 서버 다운타임은 월 4시간 이하여야 한다 (99.5% uptime)

### 4. Integration (통합)

- **I1**: Extension은 Chrome Manifest V3 규격을 준수해야 한다
- **I2**: Extension과 Dashboard는 동일한 인증 세션을 공유해야 한다
- **I3**: Supabase Realtime으로 Extension → Dashboard 데이터 동기화를 지원해야 한다
- **I4**: Claude API 호출 실패 시 graceful degradation (요약 없이 원본 JD 표시)해야 한다
